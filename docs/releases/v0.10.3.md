v0.10.3 — Say It Right

Four small fixes from the first real walk through the front door, and one for the release line itself. After a hosted login the CLI now prints commands you can actually run — `npx neat.is sync --to …`, `npx neat.is logout` — instead of a bare `neat` that isn't on an npx user's PATH; in a directory with no git remote it offers to build the graph first, then shows the push, naming the project it will add to. A registry lock held by another process is attributed to the process that holds it, not blamed on "the daemon" because a daemon happens to be running. The line printed while a daemon comes up says so — `starting the daemon for EdgeCase…` — in the same voice as `neat up`, and `neat up --json` stays one object.

For the people cutting releases: npm now processes a publish asynchronously and can take most of an hour before a version is readable. The publish workflow treats npm's "cannot publish over the previously published versions" as the confirmation it is, waits long enough for the registry, and says plainly what to do if it still hasn't appeared.

## Highlights

- **Post-login commands carry the invocation prefix** (`npx neat.is …`), enforced by a test that fails on any bare `neat` command printed under npx (#1271).
- **No remote, no snapshot → build first.** The post-login step offers to extract the directory with the same orchestrator the door's local path uses — one instrument question, whichever way you arrived — then shows the push line (#1272).
- **The lock holder is named from the lock's own PID**, "the daemon" only when it really is (#1268).
- **`starting the daemon for <name>…`** replaces "waiting on 1 project", with a progress line on a slow start; `neat up --json` emits exactly one object (#1273).
- **publish.yml survives npm's processing delay**: the exact "cannot publish over" wording counts as already published (a missing scope or OTP still fails loudly), and the visibility wait is ~30 minutes (#1270).
